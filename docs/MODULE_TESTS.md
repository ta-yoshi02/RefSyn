# モジュールとテストの対応

各モジュールについて、何をどのテストで確かめているか、何を確かめていないかを示す。
テストの実行方法と詳細は [TESTS.md](TESTS.md) を参照する。

## Kanon で実演し直さずに検証する

`tests/recordings/` の各ディレクトリが、Kanon の記録1件と、各段階で期待する結果を持つ。
`cargo test` の `tests/recorded_stage_tests.rs` が全ディレクトリを読み、段階ごとに確かめる。
事例を増やすには、ディレクトリを1つ追加すればよく、コードの変更は要らない。
必要なファイルが欠けたディレクトリは、無視せずテストの失敗にする。
形式は [tests/recordings/README.md](../tests/recordings/README.md) にある。

| ファイル | 内容 |
| --- | --- |
| `request.json` | Kanon が送った request（`docs/evaluation_cases/reruns/` からの写し） |
| `expected.json` | 段階ごとに期待する値。書いた段階と値だけを確かめる |
| `reference.mjs` | 参照実装と入力。参照との比較を期待する場合だけ置く |

| `expected.json` のキー | 確かめる段階の結果 |
| --- | --- |
| `read` | 各実演の型付き実演前状態、引数、編集列 |
| `graphs` | 各実演の操作グラフ（頂点、書込み列、戻り値） |
| `template` | 実演間の対応、各 hole の出力例、hole 付きメソッド |
| `problems` | hole ごとの escher-ts タスクと、照合する期待出力 |
| `validation` | 合成後の全体検証の結果 |
| `comparison` | 参照実装との比較の結果 |

期待値は、結果の同じ位置にすべて含まれていなければならない。
オブジェクトには余分なキーがあってもよく、配列は長さまで一致する必要がある。
満たさない位置は、事例名と経路を付けて全事例分まとめて報告する。
段階が失敗すると、その段階の結果は `{"error": ...}` になり、合成を含む後段は実行しない。
期待値に書いた後段の結果は欠落として報告される。

insert の期待値は、論文の途中結果の一部である。
引数、全実演の書込み列、第1・第3実演の頂点、対応、各 hole の出力例、各 PBE タスクで照合する期待出力を指定している。
PBE タスクの入力は指定しておらず、`paper_pipeline_tests` が論文の fixture で確かめている。
ほかの5事例は、全体検証と参照との比較だけを指定している。

参照は ES module で書き、`classSource`（参照メソッドを含むクラス）と `cases`（入力を作る関数の列）を export する。
例は `tests/recordings/*/reference.mjs` にある。
比較では、呼出し後の状態を全オブジェクトのフィールドの有無と値、参照の同一性と共有関係、戻り値または例外について比べる。
オブジェクトには一定の走査順で名前を付けるため、生成順が参照と違っても正しい解は一致する。

比べるのは、Kanon が全体検証のために記録できる状態（`Kanon/src/js/testize.js` の `captureValidationState`）に限る。
条件は次のとおりで、実行前の入力と、実行後に観測する全オブジェクトに同じく適用する。実行後には、呼出しで切り離された既存オブジェクトも含む。

- オブジェクトは対象クラスのインスタンスである。
- 自身のプロパティはすべて文字列キーで、enumerable、writable、configurable がすべて真のデータプロパティである。getter は呼ばない。
- 値は undefined、null、文字列、真偽値、`-0` 以外の有限の数値、上の条件を満たすオブジェクトへの参照のいずれかである。
- オブジェクトは拡張可能である。これは Kanon が記録しない条件で、比較器だけが追加で課している。

条件を満たさない状態は、一致とは判定しない。入力が満たさない場合と参照側の結果が満たさない場合はエラー、合成解の結果が満たさない場合は理由付きの不一致になる。
対象は symbol、`-0`、NaN、無限大、bigint、配列、Map、関数、通常のオブジェクト、アクセサ、列挙できないフィールドなどである。
Kanon はクラスをコンストラクタ名で判定するが、比較器は prototype の同一性で判定する。

各呼出しは2秒で打ち切り、生成側なら不一致、参照側ならエラーとする。比較のプロセス全体にも120秒の上限がある（打切りの経路は短い上限で回帰テストしている）。
到達できない生成物と、呼出しの途中で一時的に行った変更は観測しない。

## モジュール別

各行の「確かめていること」は、挙げたテストの assertion を読んで確認した範囲である。
「確かめていないこと」は気づいた範囲であり、網羅ではない。

### RefSyn（Rust）

| モジュール | 役割 | 確かめていること（主なテスト） | 確かめていないこと |
| --- | --- | --- | --- |
| `demonstration` | Kanon の記録を型付き状態と編集列として読む | null、undefined、フィールドの欠落を区別する。未知の参照、`validation` の欠落、版の不一致を拒否する（`paper_pipeline_tests` の `reading_*`）。実記録6件を読める（`recorded_stage_tests`） | 真偽値型と記録されたリテラルが真偽値でない場合の拒否 |
| `operation_graph` | 編集を MOLD の書込み列へ正規化する | 書込みの順序と重複を保つ。削除は共有の null 頂点への書込みになる。旧参照の不整合と未対応の操作を拒否する（`paper_pipeline_tests`）。ランダムな操作列の全 prefix で意味を保つ（`operation_graph_randomized_tests`、3,072段階）。実記録の insert の書込み列（`recorded_stage_tests`） | 単一クラス `Cell` 以外のランダム操作列。正準化はしない設計で、異なる操作列が同じグラフになることは確かめない |
| `alignment` | 実演間の対応を選ぶ | 論文の insert と同じ対応を選ぶ。種類、クラス、向き、多重度を保つ。矛盾しない最初の対応を取る。探索が上限の10,000手で打ち切られた場合を矛盾と区別して報告する（`paper_pipeline_tests`）。書込み順や生成順を入れ替えた実演でも、意味から定めた対応を取る（`operation_order_tests`、下の「操作順序の違い」）。編集種別の異なる実演で、全単射を総当たりする独立オラクルと同じ対応集合を得て、その中から選ぶ（`edit_kind_alignment_tests`、下の「編集種別の違い」） | 上限内で解が見つかる規模の範囲。対応が複数許される場合、どれを選ぶかは操作順に依存する（下の「対応の選択が操作順に依存する事例」） |
| `template` | hole 付きメソッドを作る | 論文の7文とその順序。生成が hole より前、共有頂点の束縛は1回、書込みは順序と多重度を保つ（`paper_pipeline_tests`）。実記録の insert の hole 出力例が論文と一致する（`recorded_stage_tests`） | 出力した JS を単独では実行しない。実行は全体検証と比較のテストで間接的に行う |
| `pbe_problem` | hole ごとの PBE 問題を作る | 入力に書込み前の状態、生成物、先行 hole を含み、自分と後続 hole を含まない。表現できない入力と種類の混在を拒否する（`paper_pipeline_tests`）。真偽値の型付けと、真偽値と整数・参照・文字列の混在の拒否（`boolean_values_tests`） | — |
| `escher_bridge` | escher-ts を起動する | メモリ設定の解析。runner が無い、非ゼロ終了、空の出力、JSON でない出力、形の違う JSON、入力を読まず終わらない runner を、それぞれ別のエラーにする。最後は親プロセス側の期限（`ESCHER_JS_PROCESS_TIMEOUT_MS`、既定60秒。テストでは500ミリ秒）で強制終了する（単体）。実際の起動は、合成を含む全テストで間接的に通る | escher-ts 内部の探索上限（`ESCHER_TS_TIMEOUT_MS`）が守られること自体 |
| `validation` | Node の全体検証を呼び、通らないコードを消す | 検証を通らない、または検証できないコードを返さない（`whole_method_validation_tests` の `http_*`）。runner が失敗した場合は検証せず、理由付きの `unavailable` にする（`runner_failure_tests`） | 10秒のプロセス時間制限そのもの。期限の処理は `child_process` で escher_bridge と共有し、短い期限で確かめている |
| `lib`（`handle_synthesis`、`synthesize_core`） | 段階をつなぎ応答を作る | 空の request、異なるメソッドの実演、非同型の実演を合成しない。hole ごとに1タスクを渡す（`paper_pipeline_tests`）。保存した5事例と実記録6件の合成と採用（`whole_method_validation_tests`、`recorded_stage_tests`）。runner の失敗を `list_environment_info` と検証結果に書き、コードを返さない（`runner_failure_tests`） | 合成は非同期ハンドラの中で同期的に実行する。同時要求の結果は正しいが（`http_server_tests`）、実行中はそのワーカースレッドを占有する |
| `server` | route と CORS | `routes()` を一時ポートで起動し、HTTP で確かめる。別オリジンへの CORS、Kanon の POST に要る preflight、空・JSON でない・`{}`・型違いの本文への 400 と空の応答、その他の route への 404/405、4件の同時要求がそれぞれ自分の結果を受け取ること（`http_server_tests`） | 3030番ポートへの bind（`run_server`）。Pages は使わない経路で、ローカル開発用 |
| `models` | 表示グラフの型 | request の読込みを通して間接的に使う | 専用のテスト |
| `error` | `RefSynError` | なし。どこからも使われていない | — |

## 操作順序の違い（`tests/operation_order_tests.rs`）

同じ編集を順序だけ変えた実演を、小さな `Cell` のヒープで直接書いて与える。
期待する対応、hole の型と出力、PBE の入力、テンプレートを実行した結果は、編集の意味から先に定めており、実装の出力を写したものではない。
対応と hole は頂点番号や hole 番号ではなく、各頂点が各実演で表すオブジェクトや値で比べる。

各段階の順序の扱いは次のとおりで、テストもこの区別に従う。

| 段階 | 順序の扱い |
| --- | --- |
| `operation_graph::build` | 書込みを順序と重複のまま保つ |
| `alignment::align_consistently` | 同型の判定には書込み順を使わない（論文 §4.2 の「edge order is ignored」）。hole の例が同じ入力に異なる出力を求めない最初の写像を取る。その際、各フィールドへの最後の書込みが対応先のフィールドへの最後の書込みに写る写像を優先する。見つからなければ、最初に見つかった矛盾しない写像を取る |
| `Template::build` | 第1実演の書込み順を保つ |
| `pbe_problem::build` | 実演前の状態、引数、テンプレートの生成順に並べた生成物、先行 hole の出力を与える。書込みは反映しない |
| 全体検証 | 順序が意味を持つ違いを、テンプレートが各実演を再現できるかで判定する |

| 群 | 入力 | 確かめること |
| --- | --- | --- |
| 独立した書込み | `A.other = C`、`B.other = C` を逆順にした2実演。別のフィールドと定数を含む3書込みの全順序の組（6 × 6） | 各グラフが実演の順序を保つ。対称な A と B を取り違えない。hole の型と出力、PBE 入力（receiver、実演前のヒープ、引数、生成物、先行 hole、期待出力）、テンプレート実行後の状態 |
| 生成順 | 2つのセルを receiver の後ろに挿入する `pushTwo(x, y)`。第2実演の生成順2通り × 書込み順120通り。第1実演の240通り × 第2実演2通り。両実演の 240 × 240 通りは `--ignored`（debug で約2分） | 生成物が生成順ではなくリンク構造で対応する。PBE の生成物引数がテンプレートの生成順（第1実演の生成順）に並び、ヒープの 2、3 番がその順の生成物を指す。挿入後のリスト |
| 順序が意味を持つ書込み | `A.value` への 1 → 2 と 2 → 1。1 → 2 → 1 の重複。`set(a, b)` と、引数の無い矛盾する2実演 | グラフが順序と重複を保つ。テンプレートの最後の書込みが各実演の最後の値になる。合成した `set` が `set(5, 9)` などで最後の引数を残す。同じ入力で異なる結果を求める2実演は、対応付けは通り、3つの hole は合成されるが、全体検証が第1実演を再現したあと第2実演の `A.value` の不一致で `failed` とし、コードを採用しない |
| 不正な並べ替え | 生成前のノードやリテラルの使用、旧参照が合わなくなる入替え | 対応付けの前に、グラフ作成で拒否される |
| 最後の書込みだけが違う同型 | 下の「同型でも再現しない対応」 | 宣言順で先に見つかる同型ではなく、各実演の最後の書込みを再現する同型を取る |

生成した2つのセルはどちらも `new Cell()` の状態なので、PBE 入力の JSON からはどちらがどの位置にあるかを区別できない。
生成物の配置は、対応とテンプレートの実行結果で確かめている。

`run_template` は、テスト側の実行器に hole の期待出力を与えてテンプレートを実行するもので、合成した JS の実行ではない。
このファイルで合成した JS まで実行しているのは、`set` と、下の `point` の比較だけである。
実演順序を変えて実合成まで通すのは、`recorded_stage_tests` の insert の全6順列である（下の「合成解と参照実装の比較」）。

期待値を1か所ずつ壊して、assertion で失敗することを確認した。
壊したのは、対応先、生成物の対応先と並び、最後の書込みの値、グラフの書込み順、実行後の値、PBE 入力の実演前の値、対称な書込みの対応条件である。
全体検証による拒否の検査は、検証前に止まった応答、`unavailable`、hole の合成失敗による `failed` を、拒否の理由が違うものとして受け付けないことを確かめている。

### 対応の選択が操作順に依存する事例

#### 同型でも再現しない対応（修正済み）

- 入力：`Cell {value, next, other}`、全フィールドが初期 null/0、引数なし。第1実演（receiver A、A, B, C）は `A.next = B`、`A.next = C`（editEdgeReference）、`B.other = A`、`C.other = A`。第2実演（receiver X、W, X, Z）は `Z.other = X`、`W.other = X`、`X.next = W`、`X.next = Z`。
- 同型は B → W、C → Z と、B → Z、C → W の2つある。テンプレートは第1実演の順に書くので、後者では X.next に Z、W の順に書き、最後の値が W になる。第2実演の結果は Z なので再現しない。
- 修正前：同型の判定も選択も書込み順を見ず、第2グラフの宣言順で Z を先に試すため、後者を選んでいた。初期状態が違うので hole の例の矛盾では除かれず、全体検証まで進んで失敗する。未検証のコードは採用されないが、解ける問題を落としていた。
- 修正：テンプレートの実行後の各フィールドの値は、第1グラフでそのフィールドへの最後の書込みの値である。そこで `align_consistently` は、矛盾しない組合せが見つかっても、第1グラフの各 (オブジェクト, フィールド) の最後の書込み先が対応先の (オブジェクト, フィールド) の最後の書込み先に写らなければ、それを予備として持ったまま探索を続ける。写る組合せが見つかればそれを取る。探索が尽きるか10,000手の上限に達したら、予備を取る。予備は従来の探索が返していた組合せと同じなので、従来通っていた入力を上限で落とすことはない。
- 最初の実装は、写る組合せだけを探す段階と、残りを探す段階の2段に分け、10,000手を共有していた。Codex のレビューで、第1段が上限を使い切ると第2段に進めず、従来通っていた入力が失敗すると指摘された。たとえば、値がともに 1 の別リテラル p、q に、第1実演は p → q → p、第2実演は p → p → q の順に書き、同じ対象へ書く対称な8セルを加えた入力である。最後の書込みを保つ同型は無いが、テンプレートはどちらでも 1 を残す。8! 個の同型が第1段の上限を使い切っていた。これを `trying_last_writes_first_does_not_lose_a_correspondence_found_within_the_step_limit` にした。修正前の main ではこのテストが通り、2段の実装では10,000手で失敗し、今の実装では通る。上限に達したときに予備を返す処理を外すと失敗することも確かめた。
- 最後の書込みを保つ組合せが無い入力では、従来は最初の矛盾しない組合せで止まっていた探索が、上限まで続く。結果は変わらないが、探索の時間は延びる。
- 同型の判定そのものは変えていない。論文 §4.2 は辺の順序を無視して同型を定め、どの同型を選ぶかを述べていない。今回の条件は、その選択の優先順位だけを決める。書込み列全体の一致ではなく最後の書込みだけを見るのは、途中の書込みは実行後の状態に残らないためである。たとえば 1 → 2 → 1 と 2 → 1 → 1 は列が違っても同じ値を残す。
- 必須にせず優先にとどめた理由：最後の書込みが合わない組合せしか矛盾しないものが無い場合（`contradicting_request`、引数なしの 1 → 2 と 2 → 1）、従来どおり対応付けは通り、全体検証が拒否する。値が同じ別の定数頂点に書く場合など、頂点が違っても値が一致して再現できる組合せを、対応付けの段階で落とさないためでもある。
- 確かめたこと：`of_two_isomorphisms_the_one_that_keeps_each_fields_last_write_is_taken` が、宣言順の最初の同型（`align`）が B → Z、C → W であること、`align_consistently` が B → W、C → Z を選ぶこと、テンプレートの実行が両実演の結果を再現することを確かめる。修正前の実装ではこのテストが B の対応先で失敗した。この入力では B と C が実演前状態から到達できないため、hole 1、2 は escher-ts で合成できない。合成と全体検証までは通していない。

#### receiver と対応しないセル

これは不具合とは判定していない。対応付けの契約に「receiver どうしを対応させる」は含まれず、論文の insert でも、第1実演の receiver A は第3実演の receiver でない D に対応する。

- 入力：第1実演はリスト A → B → C で、`A.other = C`、`B.other = C`。第2実演はリスト P → Q → R で、同じ2書込みを同じ順か逆順に行う。
- 観察：同じ順では A → P、B → Q、逆順では A → Q、B → P を選ぶ。初期状態が違うため、hole の例の矛盾ではどちらも除かれない。
- 確かめたこと：
  - `reordered_writes_in_different_states_reproduce_each_demonstration_whichever_cells_pair_up` が、どちらの順でも次を満たすことを確かめる。C が R に対応し、{A, B} が {P, Q} に対応し、テンプレートの実行が各実演の結果を再現する。A がどちらに対応するかは固定しない。
  - `both_write_orders_adopt_methods_that_agree_where_the_receiver_has_a_successor` が、同じ順と逆順から合成された2つのメソッドを、互いに比べる。入力は長さ2〜6のリストで receiver の後ろにノードがある30入力であり、実演と同じ状態の2入力（`[1, 2, 3]` と `[4, 5, 6]` の先頭 receiver）を含む。指定した30入力で、両メソッドが正常終了し、既存セルの `value`、`next`、`other` が一致した。
  - これは2つのメソッドの間の比較であり、独立した参照実装との比較ではない。両方が同じ誤りを持つ場合も通るので、参照仕様に対する正しさを示す検査ではない。戻り値は比べていない。
- 違いが出る場合：helper の式は異なる。逆順では hole0 が値 1 のノードの有無で分岐する。receiver が末尾にある入力では、どちらも TypeError で止まり、同じ順の版だけが止まる前に `this.other` を書く。実演はどれも receiver の後ろに2つのノードがあり、この入力は実演に含まれない。今回の比較はこの入力を検査範囲から除いているが、仕様上の対象外であるとは判断していない。
- 明示的に選んだ参照仕様との、限定した領域での比較（`both_write_orders_adopt_methods_that_match_a_chosen_reference_on_a_restricted_domain`）：
  - 検証する領域を先に「receiver の後ろにちょうど2つのセルがある」（`this.next.next.next === null`）と選んだ。実演の読み方として「receiver と後続が2つ先のセルを指す」「receiver と後続が末尾を指す」「receiver と末尾の1つ前が末尾を指す」の3つを考え、この3つが一致する領域だから選んだ。考えた3つが一致することは、実演がこの領域の意味を一意に決めた証拠ではない（他の読み方もありうる）。参照はこの領域について明示的に選んだ仕様である。
  - 参照 `tests/data/point/reference.mjs` はこのドメインの入力18件（値の組6種 × 配置3種。値の組は値 1 を含むものと重複値を含むものを含む。配置は単独、receiver の前にセルがある場合、`other` が既に張られた場合、外部から指すセルと切り離されたセルがある場合）を持つ。比較は全オブジェクトの全フィールド、別名、戻り値を見る。
  - 同じ順・逆順のどちらの合成解も18件すべてで一致した。参照の `this.next.other` を壊すと失敗する。
- 選んだ領域の外（未決定。参照を定めない）：長さ4〜6のリストの先頭 receiver で、両合成解とも3つ目の読み方（receiver と末尾の1つ前）に一致し、他の2つとは3件すべてで異なった。長さ1と2では両合成解の結果が互いにも異なる（上の「違いが出る場合」）。実演がこの範囲の意図を決めていないので、どれも不具合とは判定しない。長いリストと短いリストの扱いは未決定事項であり、決めるには仕様の決定と、それを表す実演の追加が必要である。
- 未確認：選んだ領域内で参照と異なる入力は見つけていない。receiver の保存を要件にする場合は、insert との整合を先に検討する必要がある。

## 編集種別の違い（`tests/edit_kind_alignment_tests.rs`）

`addEdge`、`editEdgeReference`、`deleteEdge`、`return` を混ぜ、意味は同じ更新を行う2実演を、小さな `Cell` のヒープで直接書いて与える。
各ケースでは、実演前状態、編集列、両グラフの書込み、許される対応のすべて、hole の型、先行 hole を除いた各実演の PBE 入力を、実行前に書いておく。
対応は頂点番号ではなく、各頂点が表すオブジェクトや値で比べる。

- オラクル：頂点集合のあいだの全単射をすべて試し、頂点の種類、クラス、定数の型、フィールド、向き、多重度、戻り値を保つものを残す。`alignment` の探索も `Vertex::corresponds` も使わない。この集合が期待の集合と一致すること、`align` が最初に見つける同型と `align_consistently` の選択がその中にあることを確かめる。
- 後段の性質：選んだ対応のもとでテンプレートを実行し、各実演の編集を直接適用した結果と一致することを確かめる。hole には期待出力を与えており、合成は行わない。

| 群 | 入力 | 期待 |
| --- | --- | --- |
| 1書込み | `A.next = null` に `addEdge(A, next, B)`、`X.next = Y` に `editEdgeReference(X, next, Y, Z)` | A → X、B → Z の1通り。第2実演の PBE 入力は更新前の `X.next = Y` を含む。旧参照先を Z とすると正規化で拒否する |
| 削除 | `deleteEdge(A, next, B)` と `deleteEdge(X, next, Y)` | A → X、null → null の1通り。削除された参照先は頂点にならない |
| 独立した書込み | `A.other = C`、`B.next = A`（`addEdge`）と、同じ更新を逆順の `editEdgeReference` で | フィールドの違う鎖なので1通り |
| 同じフィールドへの2書込み | `A.next = B` → `C` と `X.next = W` → `Z` | 同型は2通り（B → W、C → Z と B → Z、C → W）。最後の書込みを最後に保つ前者だけが第2実演を再現し、`align_consistently` は前者を取る |
| 共有 | `A.other = C`、`B.other = C` と、`P.other = Q` からの `editEdgeReference` を含む同じ更新 | 対称な A と B の2通り。どちらでも両実演を再現する |
| 循環と戻り値 | A ⇄ B の循環を `addEdge` と `editEdgeReference` で作り A を返す。第2実演は X か Y を返す | 循環だけなら対称だが、戻り値で1通りに決まる（返したセルが A の像） |
| 2生成物 | 生成した D、E で A → D → E → A。第2実演は Q、P の順に生成し `X.other = Y` から書換え | D → P、E → Q の1通り。PBE 入力の生成物はテンプレートの生成順 |
| 値と参照の3書込み | 参照2つと `C.value` 3 → 7。第2実演は別の順と種類で `Z.value` 6 → 8 | 1通りで、定数 7 が 8 に対応する |
| 5書込み | 双方向リストの `insertAfter(x)`（`other` を prev とする）。第2実演は3ノードで順序が違う | 1通り |
| 非同型 | 削除と置換、生成物と既存、別のフィールド、頂点数と書込み数が同じ別の形、片方だけの戻り値、union by rank の1書込みと2書込み | グラフは作れるが、オラクルの集合は空で、`align` と `align_consistently` も拒否する |

union by rank の1書込みと2書込みの拒否は、書込みを1対1に対応させる現仕様の制限であり、対応済みの事例ではない。
同じフィールドへの2書込みの事例は、同型であることが選択の正しさを保証しないことを示す。この入力では、宣言順でも先に見つかる方が正しい。宣言順を逆にした入力では、最後の書込みを保つ組合せを先に試すことで正しい方を取る（上の「同型でも再現しない対応」）。

src の対応付け（null と既存の取り違え、フィールドの無視、戻り値の無視、削除先の頂点化、候補順の反転）と、テストの期待値（対応先、PBE 入力の実演前の参照、先行 hole、再現の可否、オラクルのフィールド比較）を1か所ずつ壊して、assertion で失敗することを確認した。

## 合成解と参照実装の比較

`recorded_stage_tests` が、Kanon の実記録から合成し、参照実装と比べる。

リストの入力は、長さ 1、2、3、5、8 のそれぞれについて3種類の環境を用意したもの。
環境は、receiver が先頭の場合、より長いリストの途中の場合、外部から共有され切り離されたノードがある場合である。
popBack は長さ2以上に限る。

rotateRight の入力は、実演と同じく `this.left` と `this.left.right` が null でない木6種類である。

insert の記録は、3実演の全6順列でも同じ15入力で全件一致する（`every_order_of_the_insert_demonstrations_adopts_a_method_that_matches_the_reference`）。
第3実演は `next` を先に書くので、これを先頭にした2順列ではテンプレートの書込み順と hole の番号が変わる。
各順列で、hole の出力が、実演前状態から読んだ「挿入する値」「挿入位置の直前のノード」「その元の後続」の3つに（どの番号の hole かは問わず）一致すること、escher-ts が全 hole を合成すること、全体検証が3実演すべてで通ること、参照実装と一致することを確かめる。
append の記録（第2実演が `next` を先に書く）も、全6順列で採用され15入力で一致する（hole の意味の照合はしない）。
他の記録（setAt、prepend、popBack、rotateRight）は、どの実演も同じ順に書くので順列でテンプレートは変わらない。
これは記録した実演とその順序の範囲の結果であり、別の実演集合での一般化は示さない。
それぞれについて、receiver が根の場合と、別ノードの左の子の場合を試した。
4つの実演についての全体検証は通るが、`this.left.right` を求める helper が実演に特有の式になっている。
そのため、6種類の木のうち4種類で参照実装と一致しない。
これは既知の結果（同ディレクトリの README）と同じで、`expected.json` はこの不一致を期待値として書いており、テストはこれを検出できることを確かめている。
この事例のテストの成功は、既知の8件の不一致を再び検出したという意味であり、正しい右回転を合成できたという意味ではない。
全体検証を通過しても、実演していない入力で正しいことにはならない。

次の軸は、実データ構造のメソッドの評価には見つからなかった（各記録の README と上の常時テストを調べた範囲）。

- 入力に循環があるリスト。木（rotateRight）では `2026-10-30-followthrough` が循環・共有参照を含む3オブジェクトのグラフでメソッド全体を比較している（候補設定のみ。現行設定は不一致が多い）。それ以外の循環は、`edit_kind_alignment_tests` の対応付けの例と部品単体の検査にある。
- 実データ構造のメソッドでの同じフィールドへの再書込み。`Cell` の合成例（`operation_order_tests`、`edit_kind_alignment_tests`）だけ。
- 木や双方向リストの3書込みの形。
- 同順位 union の合成（拒否と、対象外の負例 0/25 だけを記録している）。順位差が2以上の実演（入力にはある）。
- swapChildren の片側の子。insertAfter の末尾。双方向リストの端（unlink では TypeError を記録するだけ）。
- 単方向リストの末尾挿入を実演として与えた場合の受理。生成ノードの `next` を明示的に書いた操作列での記録は無い。
- 長さ32を超える入力。実験記録の最大は長さ16、常時テストの多数入力比較は32。

値とヒープの大きさの偶然の一致は `2026-11-04-environment-audit` が扱う（実演の値 46〜89 と長さ 2〜5）。
