### Target programs and a known limitation

- The programs use `class Node { constructor() { this.next = null; } ... }` with fields
  `val`/`next`. The old records used `f`/`g` and `constructor(f, g = null)`; that
  constructor is also within the supported range (support depends on the state `new C()`
  produces without arguments, not on declared parameters), so the change was a choice of
  this session.
- **insert's target program was changed after a failure.** The first attempt, with
  `constructor() { this.val = 0; this.next = null; }`, was rejected before synthesis
  (HTTP 400, `addEdge on __temp1.val, which already has an edge`): the backend replays a
  created object from its `new C()` state, while Kanon's test window shows a created node
  without fields, so only `addEdge` can be demonstrated. Removing `this.val = 0` avoided the
  defect; it is **not fixed**. All five results therefore hold only for classes whose
  `new C()` leaves the fields a demonstration adds absent, null or undefined. Details and
  a minimal reproduction: `insert_general/README.md`.

## Re-evaluation

Conditions: `conditions.md`. Two preliminary runs (P1, P2) checked the measuring tools and
are not results: P1 counted a translation failure of the baseline tasks as search failure;
P2 reported per-method sums of per-task medians. The main measurement was defined after
them and before running it.

**Quantity: escher-ts backend processing time without translation** — JSON spec parsing,
job preparation, synthesizer construction and AscendRec search, summed over every task the
method needs **within one repetition**; median (min–max) over 10 repetitions.
`maxCost=32`, `timeoutMs=15000` per task, adapter search settings, same machine (not
isolated). It excludes Rust planning, translation, whole-method validation and the Kanon
edit, so it is not the total running time of either approach.

| Method | MOLD tasks | MOLD solved | MOLD time | Baseline task(s) | Baseline solved | Baseline time |
| --- | ---: | ---: | ---: | --- | ---: | ---: |
| insert | 3 | 10/10 | 17.1 ms (8.6–68.0) | env-pair | 0/10 | 15.0 s (limit) |
| append | 2 | 10/10 | 2.0 ms (1.3–6.6) | env-pair | 0/10 | 15.0 s (limit) |
| popBack | 1 | 10/10 | 1.2 ms (0.7–7.2) | env-pair | 10/10 | 5.82 s (5.56–6.58) |
| prepend | 2 | 10/10 | 0.9 ms (0.4–6.9) | env-pair + returnRef | 10/10 | 0.25 s (0.24–0.34) |
| setAt | 2 | 10/10 | 4.9 ms (3.7–13.3) | env-pair | 10/10 | 2.76 s (2.70–2.92) |

Search alone and per-task prepare/search medians: `measurements/summary.md`. Preparation
is 0.1–0.4 ms per task on both sides, a noticeable share of the millisecond MOLD totals.

What this supports: on the same problems (checked above), with the same limits and
search, every MOLD helper set was solved in all 10 repetitions within milliseconds, while
the non-separated baseline did not solve `insert` or `append` within 15 s and needed
0.25–5.8 s for the other three. What it does not: total running time (Rust planning,
validation and the edit are excluded), behaviour on inputs beyond the examples for the
baseline's terms, results on an isolated machine, or anything beyond five cases with 2–3
demonstrations each and the stated `new C()` limitation.
