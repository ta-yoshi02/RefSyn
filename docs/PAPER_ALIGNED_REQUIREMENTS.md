## 2026-10-08に確定した初期対応と着手範囲

MOLDの `deleteEdge` は通常のオブジェクト参照フィールドへのnull代入として解釈する。
初期対応にnullableな数値、文字列、真偽値フィールドを含めない。
対象クラスでnull化を許すという前提と、対象物および参照フィールドの根拠を保持する。
一般のJS型推論器やクラスの全不変条件を検証するスキーマ基盤は、最初の実装条件にしない。
クラス名とフィールド名にNode、val、nextを仮定しない。
同名fieldが複数クラスで曖昧になる場合はクラスを区別し、型を推測で上書きしない。

`addNode(C)` はクラス定義に従う `new C()` とし、生成後のフィールドを一律にnullへしない。
当面は引数なしで生成でき、決定的で、既存状態へ作用せず、生成を実演の書込みより先行しても初期値が変わらないconstructorを前提とする。
setter、Proxy、特殊なproperty、一般の副作用を持つconstructorへの対応や自動判定器は後回しとする。

複数回書込みは今回の正しさの検討と保証範囲に含めない。
高々1回という入力制限は追加せず、操作の順序と重複数を保持する。
全体検証を追加しても、有限の実演への一致と未知入力全般の正しさは区別する。

実装の順序を、R13の翻訳失敗の扱い、R15の全体検証とR16の採用条件、R01〜R03の正規化の順へ変更する。
今回、翻訳例外を `success: false` とし、native、web、Kanon埋込み版で全体検証を結果採用へ接続した。
`handle_synthesis` とbrowserラッパーでは、全実演で `validation.status = passed` となった応答だけが適用用コードを持つ。`synthesize_core` と `synthesize_browser` は検証前の候補を返す。
Kanonは呼出し前の実オブジェクトを記録し、検証情報が不足する旧payloadは反映しない。
2026-10-08のレビュー対応で、field種別と返り値を観測から補完する処理を除き、ヒープ外の副作用、addEdgeの前提、生成物の対応付け、検証不能の分類、Kanonでの適用範囲を修正した。

## 分割の基準と依存方向

`lib.rs` はRustライブラリのcrate rootである。
言語仕様として実装を書くことは禁止されないが、本プロジェクトではモジュール宣言、外部に公開する型と関数の再公開、feature条件の管理を主な責務とする。
合成の進行管理を `pipeline`、受信形式をadapter、グラフ変換と探索と環境評価をそれぞれのモジュールに置く。
ファイルを移すだけでは分離にならず、境界の入力と出力と所有する不変条件を先に定める。

2026-10-07の追加確認では `cargo check --locked --offline --all-targets --all-features` は成功し、既存の未使用関数の警告が1件残った。
`cargo check --locked --offline --no-default-features --lib` も成功し、この構成では未使用import等の警告が7件残った。
したがって「実装途中なのでRust全体がコンパイルエラー」という状態は、この2構成では再現していない。
backend未初期化によるテスト失敗、Vitest不在、IDE固有の診断、別のfeature構成は区別して確認する。

モジュールは、処理段階の名前だけで分けず、保持する不変条件と変更理由が一致する単位で分ける。
実行状態、操作グラフ、雛形、PBE問題、生成コードはそれぞれ別のデータであり、相互に代用しない。
HTTP、WASM、プロセス、JSON、Kanonエディタは境界で扱い、同型探索や雛形構成に持ち込まない。
診断用文字列は表示専用とし、後段への受渡しに再解析しない。

```text
Kanon JSON
    ↓ decode / normalize
Demonstration ──→ operation_graph ──→ alignment
                                         ↓
                                  template construction
                                         ↓
                                  statement lowering
                                         ↓
                              allocate objects in each state
                                         ↓
                 ┌── examples for the next hole ←───────────┐
                 ↓                                         │
         class/type metadata                               │
                 ↓                                         │
          escher task encoding → backend → solution         │
                                             ↓             │
                                 evaluate on each state     │
                                             ↓             │
                                  validate and bind ────────┘
                                             ↓ all holes
                              translate / assemble JavaScript
                                             ↓
                          whole-method validation on demonstrations
                                             ↓
                                  Kanon source patch
```

次のファイル配置は案であり、この文書の段階では作成しない。
`domain` は共有する識別子と値と呼び出し情報、`operation_graph` はグラフと構築、`alignment` は写像と検証を所有する。
`template` は穴付き宣言と辺と出力例、`lowering` は文列への変換、`environment` はヒープと束縛と環境評価を所有する。
`hole_examples` は実演ごとの穴入力、`escher_codec` は外部型とJSON、`backend` は合成器の起動と結果取得を所有する。
`solution` は解の構文と評価と翻訳、`composition` は雛形との組立て、`validation` は実演の期待状態との比較を所有する。
Kanonへのコード適用はKanon側のadapter、全体の進行管理は `pipeline` に置く。
小さな値型ごとにファイルを増やす必要はなく、以下の機能境界は同じモジュール内でも個別にテストできるようにする。

依存は `domain` を基礎として上記の順に向け、グラフ構築からJSON符号化、雛形からKanon UIへの依存を作らない。
`escher_bridge.rs` が現在crate rootの `FieldTables` に依存しているような配置は、共有型の所有箇所を決めてから移す。
nativeとbrowserは同じ問題と翻訳規則を使い、起動adapterだけを分ける。
名前や参照番号を境界で変更する場合は、変更前後の対応表をデータとして保持する。

## 対応付け規則と既存ライブラリ

以前の方針としてユーザが述べた「対応する部分が最大のものを共通部分にする」は、現行の部分対応探索と整合する。
しかし、現在の論文4章の有効本文は、対象頂点の全単射が辺の向きとフィールド名と重複数を保存し、同型がなければ失敗すると規定する。
最大共通部分を探す問題と、全体の同型写像を選ぶ問題を同じ契約にしない。
論文への適合が必須なので、設計案は現行本文の同型条件を基準にする。
複数の全同型写像があれば保存される辺数はどれも同じであり、「最大」はその間の選択基準にならない。
対応の非一意性と、その対応が意図した状態更新を表すかの検証は別に残る。

既存依存の `petgraph 0.6.5` にはVF2による `is_isomorphic_matching` と、写像を返す `subgraph_isomorphisms_iter` がある。
ローカルの固定版ソースで確認した。
前者の返り値は真偽値なので、後段で使う頂点写像の取得にはそれだけでは足りない。
後者は部分グラフの写像APIであり、全体の同型に使うなら頂点数と辺数と写像の全域性を検証する必要がある。
これらのAPIの文書は多重グラフを対象外としているため、論文の反復書込みをそのまま並行辺にして投入する方法は採らない。

第一候補は、各書込みを独立した頂点にし、対象頂点と書込み頂点をfrom/toの役割付き辺で結ぶ単純有向グラフへの変換である。
書込み頂点にはフィールド名を持たせ、対象頂点には型とクラスと既存／新規の属性を持たせる。
同じ書込みの繰返しは異なる書込み頂点として残す。
この変換が元の操作グラフの同型条件と同値か、自己参照、反復辺、未使用の生成頂点を含めてテストしてから採用する。
この案とAPI利用はまだ実装していない。
公式API文書は [is_isomorphic_matching](https://docs.rs/petgraph/latest/petgraph/algo/isomorphism/fn.is_isomorphic_matching.html) と [写像列挙](https://docs.rs/petgraph/latest/petgraph/algo/isomorphism/fn.subgraph_isomorphisms_iter.html) を参照できるが、実装ではロックされた0.6.5のソースと挙動を基準にする。

## 各機能の入力と出力と受入条件

| ID | 機能 | 入力 → 出力 | 受入条件と失敗条件 |
| --- | --- | --- | --- |
| R01 | 受信と検証 | Kanon JSON → 型付き呼び出しと編集記録 | 必須データと操作ごとの必須項目を検証。不明な操作を無視して成功にしない |
| R02 | 識別子の正規化 | 呼び出しとID対応表 → 正規化済み実演 | 入力物と生成物を区別し、同じ参照の共有を保存。重複ID、曖昧な対応、参照先欠落を検出。実演の内容を推測で補正しない |
| R03 | 操作グラフ構築 | 正規化済み操作列と呼び出し前状態 → 頂点宣言列と書込み辺列と由来情報 | 既存と生成と型付き値とnullを区別。書込み順序と重複数を保存。初期環境の辺を操作グラフの辺と混同しない |
| R04 | 対応付け | 複数の操作グラフ → 第1実演から各実演への全単射 | 対象頂点、型とクラスと既存／新規、辺の向きと名前と重複数を保存。非同型は失敗。辺の順序は同型判定に使わない |
| R05 | 雛形と穴出力 | グラフと写像 → 雛形と穴ごとの型付き出力例 | 既存オブジェクトとプリミティブは値が実演間で同じでも穴にする。同じ頂点の出現は同じ穴。生成とnullを固定。第1実演の宣言順と辺列を保存 |
| R06 | 文列への変換 | 雛形と固定した穴順 → 型付き文列と局所変数対応表 | 全生成→全穴束縛→全書込み。生成は宣言順、書込みは辺列順。各穴は一度評価。名前の衝突や欠けた穴を拒否 |
| R07 | 生成後環境の構築 | 各呼び出し前環境と文列とクラス情報 → 各実演の生成後環境 | 全生成物を最初の穴の入力に含める。既存参照は不変。生成直後のフィールド値を実際の生成規則と一致させ、書込みはまだ実行しない |
| R08 | 穴の入出力例の構築 | 全実演の現在環境と対象穴と対応出力 → 一つの型付きPBE問題 | 一つの穴について全実演を集める。生成物と全先行束縛を含める。環境と期待出力の参照体系を一致させ、期待値を入力に追加しない |
| R09 | 合成用型と部品の定義 | クラス情報と実行状態のフィールド情報と穴の型 → 合成用クラスと関数シグネチャと部品集合 | クラス名とフィールド型の根拠を保持。未知の型を整数として埋めない。利用可能な読取り関数を定義し、合成された処理と供給したライブラリを区別 |
| R10 | PBE問題の符号化 | 型付き問題と合成用型 → escher-ts task JSONと参照対応表 | JSONを復号した意味が元の問題と一致。負数、false、null、undefined、文字列、参照を潰さない。backendが表現できない型は明示的に失敗 |
| R11 | 合成器の実行 | taskと探索条件 → 解または型付き失敗 | タイムアウト、解なし、不正task、実行失敗を区別。同じ問題をnativeとbrowserへ渡す |
| R12 | 解の検証と環境への束縛 | 解と各入力環境と期待出力 → 各実演の次の環境 | 合成式を各入力で評価して出力と比較し、型と参照を検証してから束縛。全実演の束縛後に次の穴を作る。出力例を無条件に代入して評価を省かない |
| R13 | 解の翻訳 | 解の構文木と型と変数対応 → JavaScript式または補助メソッド | 解の評価と同じ値と参照を返す。未対応構文や部品は翻訳失敗。表示文字列の解析で代用しない |
| R14 | コード組立て | 文列と全穴の翻訳結果 → メソッドと必要な補助定義 | 束縛順と書込み順と共有を保存。未解決穴、名前衝突、未定義helperを拒否。メタデータから代入を追加しない |
| R15 | 全体の意味検証 | 生成コードと各実演の呼び出し前状態と期待最終状態 → 検証結果 | 値、参照同一性、全対象オブジェクト、外部の別名参照、生成数、返り値を対象仕様に応じて比較。穴の成功を全体の成功と同一視しない |
| R16 | Kanonへの反映 | 検証済みコードと対象メソッドの識別情報と元ソース版 → ソース変更と再実行結果 | 対象メソッドと必要な補助定義だけ変更。対象曖昧、元ソース変更、検証失敗なら適用しない。再実行結果を確認 |

R15の実演再現は実装の品質条件として追加する。
2026-10-08の調査時点では本番成功判定にR15がなかったため、今回、共有JS検証器をnativeとbrowserの採用判定へ接続した。
既存の候補生成テストと未知入力での実行テストは残し、本番の採用条件を検査するテストとは分ける。
論文1〜5章に「全体を自動検証するアルゴリズムが既に定義されている」とは読み替えない。
有限の実演再現によって、任意の入力での正しさが証明されたとも扱わない。

## 境界で交換するデータ

以下は意味の定義であり、Rust型名やJSONの具体的なスキーマは未確定である。
生の受信形式と内部モデルとescher-tsの形式を分ける。

| データ | 含める情報 | 渡す境界 |
| --- | --- | --- |
| 呼び出し情報 | 実演ID、メソッドとクラス、呼び出し文脈、レシーバ、順序付き引数、引数名と型 | R01→R02、R07、R09、R16 |
| 実演 | 呼び出し情報、呼び出し前ヒープと変数束縛、編集列、ID対応、クラス情報、期待最終状態またはその算出元 | R02→R03、R07、R15 |
| 操作グラフ | 順序付き頂点宣言、順序付き書込み辺、元の編集位置とIDへの由来情報 | R03→R04→R05 |
| 対応結果 | 各実演への頂点全単射、同型条件の検証結果 | R04→R05 |
| 雛形構築結果 | 宣言と辺、穴IDと元頂点、穴の型、各実演の対応値、固定した穴順 | R05→R06、R08 |
| 文列 | 生成と穴束縛と書込み、頂点から局所変数への対応、穴ID | R06→R07、R14、R15 |
| 穴入力環境 | 呼び出し情報、生成後ヒープ、元の変数、生成局所変数、先行穴の局所変数 | R07とR12→R08 |
| PBE問題 | 穴ID、順序と型を持つ入力、出力型、実演ID付き入出力例、クラス定義、部品集合 | R08とR09→R10 |
| 符号化結果 | task JSON、引数位置と名前と型、内部参照とbackend参照の対応 | R10→R11、R12、R13 |
| 解 | 穴ID、構文木、型、入力シグネチャ、解なしや翻訳失敗等の段階別状態 | R11→R12、R13 |
| コード結果 | 対象メソッド、メソッド定義、必要な補助定義、生成元実演、元ソース版、検証結果 | R14とR15→R16 |

「状態」は呼び出し前、全生成後、先行穴束縛後、実演の期待最終状態を明示して区別する。
操作列の途中状態を、文列が穴を評価する状態の代わりに使わない。
参照の比較は単なる値列比較にせず、既存物の対応と新規物の対応を保った比較にする。

穴入力の一般規則は、呼び出し前環境に全生成物とその局所変数束縛を追加し、さらにその穴より先に合成した式の評価結果を追加することである。
`insert`の7文では、最初の穴の入力はnew後、次の穴の入力はnewとvalueの束縛後、最後の穴の入力はnewとvalueとprevの束縛後になる。
上の4文を実行すると全穴の結果が揃うが、各穴の合成入力に自分自身や後続穴の結果を入れることはしない。
既存オブジェクトのフィールドと新規オブジェクトのフィールドは、その間の代入文によって変更しない。

## 必要なテストと証拠

以下は接続段階ごとの受入条件の一覧であり、すべてが実装済みという意味ではない。
最初の単位に全項目を要求せず、変更が保証する性質からテストを選ぶ。複数回書込みは列の保持を確認しても、その意味保存の保証には数えない。
各段階のテストは入力と期待結果を明示し、隣接する段階が同じ誤りをしても通る往復テストだけにしない。
JSONの往復に加えて、backend側の実際の型解釈と評価も照合する。

| 要件 | 個別テストの対象 |
| --- | --- |
| R01〜R03 | 不完全入力、不明操作、ID衝突、実演をまたぐID、同じ参照の共有、値型、null、更新の正規化、未使用の生成頂点、辺の順序と重複、複数クラス |
| R04 | 頂点名変更で不変、書込み順変更で同型、辺の向きや名前や重複数の違いで非同型、クラスと型と既存／新規の不一致、複数実演、対称なグラフ、非同型で失敗 |
| R05〜R06 | 全実演で同値でも穴、頂点共有時の穴共有、異なる頂点を勝手に共有しない、固定null、複数生成、全写像からの出力取得、7文、反復辺、フレッシュな名前 |
| R07〜R08、R12 | 各穴の入力全体、生成物の初期値、先行結果と参照、先行穴失敗時に後続を作らない、複数実演を一問題にする、出力不一致、未対応初期化の拒否 |
| R09〜R11 | 非標準のクラス名とフィールド名、クラス間参照、receiverと引数、文字列や真偽値や負数、undefined、null、脱落した参照、task型、実際のbackend復号、解なしとタイムアウト |
| R13 | 各対応構文と部品について元の解と翻訳後を同じ入力で実行し、値と参照を比較。演算子の優先順位、変数の捕捉、条件分岐、未対応構文、実物の参照を返すこと |
| R14〜R15 | 全実演を初期状態から実行。insert、値交換、参照張替え、別名参照、到達不能物、null、複数生成、再実行。参照の共有と返り値、未解決helper、翻訳失敗の扱い |
| R16 | 対象だけを変更、補助名衝突、元ソース版の違い、失敗時に変更しない、Kanon再実行、UIでの反映 |

単体テスト、境界を通す結合テスト、Kanonから再実行までのE2Eを別々に記録する。
テスト件数、spec生成成功、PBE成功、翻訳成功、全体検証成功、エディタ反映成功を別の指標にする。
意味を検査するテストでは、実装が出力した文字列を正解として再利用しない。

既存テストは「保持」「契約に沿って修正」「意味検査に置換」「旧経路とともに削除」の4区分で棚卸しする。
件数やテスト名だけで価値を判定せず、誤った対応や環境やコードを与えた場合に失敗するかを確認する。
具体的には `operation_analysis_tests.rs::test_operation_analysis_basic` は、結果の意味をassertせず、解析と表示が成功することを検査している。
同じファイルのdetailedテストは差分数の下限と操作数だけを検査し、正しい対応や環境の内容を保証しない。
このようなテストは動作確認としての役割と意味的な保証を区別し、論文契約のテストの代わりに数えない。
コードの文字列比較も、文順序や名前の契約を直接検査する場合には必要なので、一括して削除しない。

## 実装前に解決する設計項目

1. **受信スキーマとIDの寿命**：Kanonの実際の記録元で、呼び出し前状態、クラス情報、レシーバと引数、ID対応を確認する。
   固定コミットの送信フィールドは確認済みだが、`precondGraph` と `actualGraph` の記録時点と、実演をまたぐID対応の意味は記録元まで追って検証する必要がある。
2. **編集の正規化**：`addEdge`と`editEdgeReference`を論文の書込みへ変換し、MOLDの`deleteEdge`を固定nullへの書込みへ変換する。
   Kanonの現行property削除とは区別し、期待状態と反映をMOLDの意味へ揃える。変数更新と返り値の拡張はこの最初の単位へ含めない。
3. **穴順と対応の選択**：穴順を一度決定して全処理で共有する。
   複数同型対応は一つを選ぶという論文の規定を守り、再現可能な選択規則を定める。
   穴の成功で別の対応を探索する機能は、論文の規定への追加として扱う。
4. **クラスの初期化**：型宣言と生成直後の実行状態は別データである。
   初期対応のconstructor前提は上記の範囲とし、対応するクラスの実際の初期値を保持する。試作の既定値mapが一般のconstructor評価を実装しているとは扱わない。
5. **backendの型と値表現**：escher-tsの固定版で、実際に受け入れる型とundefinedの表現と解の構文を確認する。
   unsupportedな値を `-1` やnullに置き換えて動かす方法は採らない。
6. **解の形式とKanonへの反映**：backendの構文木をどこで保持し評価するか、翻訳結果を式として使うか補助メソッドとして使うかを定める。
   生成局所変数と先行穴を解へ渡せることを確認する。
   メソッドの識別、ソース版、補助定義の適用先はKanon側の契約で定める。

未決項目は、それに依存するコードの実装前に実データと固定版ソースで解決する。
未確認の受信仕様やbackend仕様を、現在の動作から推定して確定しない。
ユーザはRefSyn側でのサブモジュール初期化と依存関係の読み込みを許可している。
レビュー時にも固定バージョンの初期化とロックファイルに従うインストールを行ってよい。
依存の更新やサブモジュールの参照変更とは区別し、変更が必要になった場合は報告する。

## 小さな置換の進め方

翻訳失敗の拒否と全体検証の採用条件を先に実装し、次の単位の着手条件を以下に限定する。
新しい包括的レビューの反復を着手条件にしない。未確認事項は、それに依存する境界を接続するときに解決する。

次は、既知の対象物と参照fieldの情報、およびdeleteEdge記録を入力し、由来付きの固定null書込みまたは理由付き失敗を返す境界を作る。
同じ契約で環境更新を検査し、未知fromでは失敗、値fieldをPointerへ変更しない、対象slotだけをnullにすることを確認する。
property、参照先、外部alias、他fieldを保持し、不正入力では状態を変更しない。
null頂点を共有する規則を定め、操作の順序と重複数を保持する。
テスト本数は固定せず、以上の保証に必要な検査を選ぶ。
次にR03の他の操作とR04、R05へ接続し、null同士の対応、nullと非nullの非対応、頂点ごとの穴を検査する。
前回の試作はR06とR07の一部に相当するので、この全体契約に照らしてデータ型と責務を再点検してから再利用する。
R08以降は、各境界に明示的なデータと個別テストを用意し、順に接続する。
穴入力では書込み前の参照を保持し、生成後環境ではconstructorの実初期値を保持する。
今回追加した採用条件を通すことと、正規化単位の不正入力時の状態不変などを個別に検査することを両立する。
旧経路の削除と本番切替は、該当する個別テストと境界テストと実演再現が通った単位ごとに行う。

コードの命名と構造はHow、テストの名前と検証はWhat、コミットメッセージはWhy、コードコメントはWhy notを記す。
コードコメントで単に処理の手順を繰り返さず、採らなかった方法の制約を必要な箇所だけに残す。
