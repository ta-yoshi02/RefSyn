## レビュー項目

1. 実際の呼出し経路と依存を確認してください。
   lib.rsが受信、正規化、グラフ構築、対応付け、差分推定、問題生成、組立て、プロセス起動のどれを担うかを列挙してください。
   unify_ops、isomorphism、operation_analyzer、synthesis_templateの使用先を、本番、代替経路、example、テスト、公開APIに分けてください。
   名前やコメントから使われていると推定せず、呼出しを確認してください。

2. モジュールの責務と交換データをレビューしてください。
   処理の関数を別ファイルへ動かすだけでなく、各モジュールが所有する型と不変条件、依存方向、公開API、失敗条件を確認してください。
   実行時ヒープ、操作グラフ、雛形、PBE問題、解、生成コードを混同していないか確認してください。
   16の機能境界が適切か、細分化が必要か、過剰な分割がないかを判断してください。
   新規試作の型、文列構成、環境評価を同じモジュールに置いた判断もレビュー対象です。

3. 論文の対応付けと雛形規則への適合を検査してください。
   グラフの対象頂点、型とクラス、既存／新規、辺の重複、自己参照、同じ頂点の共有、同じ値を持つ異なる頂点を確認してください。
   複数実演への写像と穴の出力例を追い、同値の既存参照やプリミティブまで穴にする規則を検査してください。
   複数の対称な対応、宣言順、穴順、辺列順、反復書込みが結果へ与える影響を確認してください。

4. 既存ライブラリの利用を評価してください。
   既存依存のpetgraph 0.6.5のVF2と写像取得APIを第一候補として検討してください。
   真偽値しか返さないAPI、多重グラフを扱わないという制約、部分グラフAPIと全体同型の差を確認してください。
   書込みごとに独立した頂点を作る単純有向グラフへの変換案が、論文の同型条件と同値か検査してください。
   自己参照、反復書込み、役割付き辺、未使用の生成頂点を含めて評価してください。
   別の適切な既存実装がある場合は、公式資料と固定版ソースを根拠に比較してください。
   ライブラリ採用や依存更新は実施せず、採否と必要な検証を報告してください。

5. 環境生成とPBE接続を追跡してください。
   KanonのprecondGraphとactualGraphの記録時点、ID対応の寿命、レシーバと引数、クラス情報を記録元まで確認してください。
   全newの先行、生成物の初期値、undefinedとnullの区別、先行穴の結果の束縛を検査してください。
   全実演の同じ穴を一つの問題にし、解を各環境で評価してから次の穴へ進む設計か確認してください。
   JSON符号化で負数、真偽値、文字列、null、undefined、別名参照、生成物が失われないか確認してください。
   backendが表現できない値やコンストラクタの初期化を、根拠のない既定値で補っていないか検査してください。

6. 解の評価、翻訳、組立て、Kanon反映を検査してください。
   解の構文木の評価と翻訳後のJavaScriptの評価が、値と参照について一致するか確認してください。
   生成物や先行局所変数を解へ渡せるか、名前衝突、捕捉、未解決helper、未対応構文を確認してください。
   PBE成功、翻訳成功、組立て成功、全体検証成功、エディタ反映成功を区別してください。
   メタデータからの代入補完、文順序の変更、部分的な解だけでの反映等の問題を確認してください。

7. テストを中身で棚卸ししてください。
   「保持」「契約に沿って修正」「意味検査に置換」「旧経路とともに削除」に分類し、具体例と理由を示してください。
   件数や名前、文字列の存在、JSON生成成功、穴の合成成功を正しさの代用にしないでください。
   文順序等を検査する文字列比較まで一括して無意味と判定しないでください。
   値と参照と返り値、外部の別名参照、到達不能物、重複値、複数生成、順序に依存する更新を比較するテストを優先してください。
   保存済み生成コードの再実行と、現在のソースから再合成した結果を区別してください。
   可能なら誤った対応や順序を与えて既存テストが検出するか、一時的な再現スクリプトで確認してください。

8. ビルドと置換計画をレビューしてください。
   通常、server無効のライブラリ、native、browser/WASMを区別し、コンパイルエラー、警告、環境不足、意味的な失敗を分類してください。
   小さな置換の順序と各段階の完了条件、既存APIとの接続方法、旧処理の最終削除条件を提案してください。
   旧処理は全体の実演再現と構成別の確認が済むまで削除しないでください。
   Howはコードの構造、Whatはテスト、Whyはコミット、Why notはコメントという方針も評価してください。
